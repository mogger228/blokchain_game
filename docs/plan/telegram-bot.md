# Plan: Telegram-игра на учебном блокчейне

Статус: `review-deep` PASS (три независимых ревьюера), 2026-10-06

Основание: `docs/design/telegram-bot.md`, подтверждён пользователем 2026-10-06.

## Gate 0. Сохранность исходных данных

1. Зафиксировать текущую схему и количество блоков в существующем `chain.db`, когда будет доступен Python/SQLite.
2. Все тесты выполнять только с временными БД через `BLOCKCHAIN_DB_PATH`; не изменять пользовательский `chain.db`.
3. Не менять поля таблицы `blocks`, алгоритм хеширования и представление `float`, чтобы старые блоки продолжали проходить валидацию.

Критерий: существующая БД не записывается тестами и остаётся читаемой после добавления новых таблиц.

## Шаг 2. Аддитивная миграция хранилища

Файл: `storage.py`.

Изменения:

1. Сделать `get_connection()` параметризуемым путём из конфигурации и включить `PRAGMA foreign_keys = ON` и разумный `busy_timeout`.
2. Оставить `blocks` без изменения.
3. В `init_db()` выполнить идемпотентные `CREATE TABLE IF NOT EXISTS`:

```sql
CREATE TABLE players (
    telegram_id INTEGER PRIMARY KEY,
    username TEXT NOT NULL COLLATE NOCASE UNIQUE,
    registered_at TEXT NOT NULL,
    initial_block_index INTEGER NOT NULL UNIQUE,
    FOREIGN KEY(initial_block_index) REFERENCES blocks("index")
);

CREATE TABLE processed_actions (
    action_key TEXT PRIMARY KEY,
    actor_id INTEGER NOT NULL,
    action_type TEXT NOT NULL,
    request_fingerprint TEXT NOT NULL,
    block_index INTEGER NOT NULL UNIQUE,
    created_at TEXT NOT NULL,
    FOREIGN KEY(block_index) REFERENCES blocks("index")
);
```

4. Определять необходимость генезис-блока по отсутствию строк в `blocks`, а не по наличию файла.
5. Добавить внутренние функции, работающие на переданном соединении: чтение цепочки, последнего блока, игрока по Telegram ID/username, вставка блока/игрока/action receipt. `_insert_block(conn, block)` никогда не вызывает `commit`; единственный commit находится на границе use case. Публичный legacy-helper `save_block()` при необходимости открывает и завершает собственную транзакцию и не используется составными операциями.
6. Добавить публичные read-only операции `get_block_by_index()` и получение страницы игроков.
7. Все составные записи выполнять через один `BEGIN IMMEDIATE` с rollback при исключении.

Путь upgrade: первый `init_db()` добавляет две таблицы в непустую старую БД без изменения `blocks` и данных.

Rollback к старой версии кода: аддитивные таблицы остаются в БД, потому что старый код их игнорирует. Автоматический destructive downgrade не предоставляется: удаление `players`/`processed_actions` потеряло бы регистрацию и идемпотентность. Если оператору нужна именно старая схема, README требует предварительную полную копию БД; восстановление выполняется только возвратом этой копии. Повторный upgrade после запуска старого кода сохраняет метаданные игроков и receipts.

Проверки:

- новая пустая БД получает три таблицы и ровно один генезис;
- повторный `init_db()` ничего не дублирует;
- fixture старой БД только с `blocks` обновляется без изменения строк и хешей;
- старая версия read/CLI-кода работает после upgrade при оставленных дополнительных таблицах;
- цикл upgrade → регистрация/операция → запуск старого read-кода → повторный upgrade не выдаёт вторые `$100` и сохраняет receipts;
- инъекция ошибки строго после `_insert_block` и до вставки player/receipt не оставляет частичных данных.

## Шаг 3. Прикладной сервис

Новый файл: `service.py`.

Типы и ошибки:

- dataclass `Player`;
- dataclass `PlayerBalance`;
- `ValidationError`, `NotRegisteredError`, `PlayerNotFoundError`, `InsufficientFundsError`, `ChainIntegrityError`, `ForbiddenError`, `IdempotencyConflictError`.

Операции:

1. `initialize()` вызывает идемпотентный upgrade хранилища с возможностью создать новую БД; его вызывают только Telegram bot startup и CLI `init`. `require_existing_database()` проверяет наличие `blocks` без создания файла/таблиц и используется всеми остальными CLI-командами.
2. `normalize_username()` удаляет один `@`, приводит значение к нижнему регистру и принимает только Telegram-совместимый шаблон `[A-Za-z0-9_]{5,32}`; каноническое имя блока — `@username`.
3. `register_player(telegram_id, username)` под `BEGIN IMMEDIATE`:
   - возвращает существующего игрока для того же Telegram ID без начисления;
   - отклоняет занятый другим ID username;
   - проверяет цепочку;
   - создаёт `system -> @username` на `100.0`;
   - вставляет игрока с ID стартового блока;
   - фиксирует обе записи одним commit.
4. `create_player_transaction(telegram_id, recipient_username, amount, action_key)` под `BEGIN IMMEDIATE`:
   - сначала авторизует actor и канонизирует все параметры;
   - вычисляет fingerprint из `action_type`, `actor_id`, sender, recipient и конечного представления amount;
   - при существующем `action_key` возвращает старый блок только при полном совпадении actor/type/fingerprint, иначе бросает `IdempotencyConflictError`;
   - получает sender только из `players`;
   - требует зарегистрированного recipient;
   - проверяет положительную конечную сумму, запрет self-transfer, целостность и актуальный баланс;
   - вставляет блок и `processed_actions` в одной транзакции.
5. `create_admin_grant(admin_telegram_id, recipient_username, amount, action_key, configured_admin_id)` до чтения receipt повторно проверяет числовой ID, затем применяет ту же проверку fingerprint и атомарно создаёт `system -> @username` и receipt.
6. `create_trusted_transaction(sender, recipient, amount)` сохраняет прежнюю CLI-семантику произвольных строк и неограниченного отправителя `system`, но выполняет validate/read balance/create index/insert под единым `BEGIN IMMEDIATE`.
7. Получение списка игроков с балансами читает страницу игроков и единственный snapshot цепочки внутри одной read-транзакции; все балансы страницы вычисляются по этому snapshot.
8. Добавить чтение своего баланса, блока по ID, полной цепочки и результата валидации.
9. Все суммы остаются `float` для совместимости, но `NaN`, `Infinity` и `-Infinity` запрещаются через `math.isfinite`.

Проверки:

- регистрация, повторная регистрация, конфликт ID/username, отсутствие username;
- начальный баланс ровно `100`;
- успешный перевод и недостаточный баланс;
- нулевая, отрицательная, бесконечная и NaN-сумма;
- self-transfer и незарегистрированный получатель;
- разрешённое/запрещённое административное начисление;
- один action key создаёт ровно один блок при последовательном и конкурентном повторе;
- одинаковый action key с другим actor/type/recipient/amount получает конфликт и ничего не записывает;
- повреждённая цепочка блокирует любые новые записи;
- пагинация списка игроков и расчёт балансов.
- конкурентные тесты на двух SQLite-соединениях: одинаковый username от разных ID, один ID с разными регистрациями, два допустимых по отдельности перевода с общей суммой выше баланса, player transfer одновременно с admin grant, два `init_db()` и CLI append одновременно с ботом;
- snapshot-тест не допускает смешения страницы игроков и цепочки при параллельной записи.

## Шаг 4. Сохранение CLI

Файл: `main.py`.

Изменения:

1. Сохранить команды `init`, `send`, `balance`, `chain`, `validate`.
2. Добавить `transaction --id N`.
3. Только `init` вызывает `initialize()`. Команды `send`, `balance`, `chain`, `validate`, `transaction` сначала вызывают `require_existing_database()` и при отсутствии БД сохраняют прежнюю ошибку и ненулевой exit code, не создавая файл и не применяя миграцию.
4. Направить `send --from ... --to ...` в атомарный `create_trusted_transaction()`, сохранив произвольные исторические имена и особое поведение точного имени `system`.
5. Сохранить понятные русскоязычные сообщения и ненулевой exit code для ошибок CLI.

Проверки:

- subprocess/smoke-тест полного прежнего сценария `init → system send → user send → balance → chain → validate` на временной БД;
- старые имена команд и аргументы продолжают работать;
- поиск существующего и отсутствующего ID.
- каждая команда, кроме `init`, при отсутствии БД возвращает прежнее понятное сообщение/ненулевой код и не создаёт `chain.db`;

## Шаг 5. Telegram-представление

Новые файлы:

- `bot.py` — точка входа и регистрация handlers;
- `bot_handlers.py` — диалоги и callbacks;
- `formatters.py` — безопасное форматирование сообщений и разбиение цепочки.

Изменения:

1. До сборки/запуска polling вызвать `initialize()`, затем собрать `Application` через `ApplicationBuilder` и явно установить последовательную обработку updates.
2. `/start`:
   - принимать только private chat;
   - сначала искать существующего игрока по `effective_user.id`; он продолжает работать с зафиксированным игровым именем, даже если текущий Telegram username удалён или изменён;
   - только для нового ID регистрировать `effective_user.username`, а при его отсутствии показывать инструкцию без записи в БД;
   - показывать стартовый баланс и главное меню.
3. Реализовать диалог перевода: recipient → amount → confirmation. Sender всегда берётся сервисом по Telegram ID.
4. Реализовать кнопки своего баланса, поиска ID, показа цепочки, проверки цепочки и правил. Поиск ID повторяет ввод при нецелом/отрицательном значении, сообщает об отсутствующем ID, отдельно обозначает генезис `#0`, а для найденного блока выводит время, sender, recipient, amount, hash и previous hash.
5. Реализовать `/cancel` и отмену кнопкой на каждом stateful шаге.
6. Для confirmation генерировать случайный action key, включать его в callback data и хранить неизменяемый pending intent в `user_data` по этому ключу. Новый сценарий и `/cancel` инвалидируют предыдущие intents и клавиатуры; callback принимается только если его ключ совпадает с активным intent, иначе отвечает «действие устарело». После ответа inline-кнопки удаляются. Сервис остаётся последней защитой от повторной доставки.
7. Экранировать пользовательские значения или отправлять их без parse mode, чтобы username не ломал разметку.
8. Делить длинную цепочку на сообщения с безопасным запасом ниже лимита Telegram.
9. Не логировать токен и полные тексты пользовательского ввода.

Проверки:

- handler-тесты через синтетические Update/CallbackQuery без сети;
- `/start` с новым, существующим и отсутствующим username;
- полный happy path и ошибки перевода;
- отмена из каждого состояния;
- старый callback после нового сценария и после `/cancel` не создаёт блок;
- поиск по ID покрывает нецелое/отрицательное значение, отсутствие, генезис и полный обычный блок;
- длинная цепочка разбивается без потери блоков;
- группа не регистрирует игрока и предлагает private chat.

## Шаг 6. Админ-панель

Файл: `bot_handlers.py`.

Изменения:

1. Показывать `🛠 Админ-панель` только настроенному ID, но не считать скрытие кнопки проверкой безопасности.
2. На входе каждого admin callback и перед commit вызывать проверку ID в сервисе.
3. Показать страницы по 10 игроков с балансом и кнопками навигации.
4. Реализовать начисление: выбор игрока из страницы или ввод username → `$10`/`$50`/`$100`/другая сумма → confirmation.
5. Административный action key проходит через тот же механизм `processed_actions`.
6. Не позволять начисление отсутствующему игроку. Зарегистрированный username `@system` не смешивается с техническим sender `system` и обрабатывается как обычный получатель.

Проверки:

- не-администратор не видит панель и получает отказ на вручную сформированный callback;
- подмена callback после открытия панели также получает отказ;
- навигация не выходит за границы страниц;
- preset и произвольная сумма создают правильные `system`-блоки;
- повторное подтверждение возвращает первоначальный ID без нового блока.
